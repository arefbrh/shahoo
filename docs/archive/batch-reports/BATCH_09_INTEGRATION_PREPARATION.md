# Batch 09 integration preparation — source-only handoff

**Status:** Documentation only. No integration, route, environment setting, schema or application logic was added or enabled. Batch 09 is to follow Batch 08 and is not implemented here. Findings below describe source code, not a running deployment; no live functionality or provider contract has been verified. Section 7 of the owner's Batch 04 brief is the task basis. Source, not older reports, is authoritative.

## 1. Actual checkout → unpaid order

1. `src/components/site/cart-view.tsx` links to `/checkout`. `src/routes/checkout.tsx` loads `getCheckoutContext` (`src/server/commerce/api.ts`), which calls `checkoutContext` in `src/server/commerce/checkout.ts`. It resolves a customer or guest cart, account and owned saved addresses, and active, approved shipping methods. If no valid shipping method exists, checkout cannot submit.
2. `src/components/site/checkout-view.tsx` requests a debounced server quote through `quoteCheckoutFn` for shipping/coupon selection. This is a preview, not the authority for the final charge. Its form sends recipient/address, shipping method, coupon and a UUID checkout key stored in session storage to `placeOrderFn`. The Zod schema is in `src/server/commerce/api.ts`; no payment details or client-supplied prices are accepted.
3. `placeOrder` resolves the cart and customer again. `commitCheckout` validates address, saved-address ownership, customer mobile and coupon; its replay check uses the checkout key and the cart's buyer key. The transaction locks the cart, rereads current product/variant/category availability, price, stock and approved shipping, validates the coupon, conditionally increments its usage, calculates totals in integer **IRR**, inserts the order and item snapshots, and conditionally reserves inventory. It records inventory/order/audit events and an **internal** notice, and removes exactly the cart lines consumed. Failures roll back the transaction. The new order is `status=awaiting_payment`, `paymentStatus=unpaid`, `stockState=held` with a 24-hour hold; coupon usage is consumed at order creation.
4. After success, `placeOrder` saves a guest receipt token in the HttpOnly `shahoo_receipts` cookie and returns only the public order code. The UI removes its checkout key, calls `notifyCart(0)`, and navigates to `/order/{publicCode}`. Replaying the same key for the same buyer reopens the receipt; another buyer is rejected. No payment-start, gateway redirect or callback is invoked by checkout.
5. `src/routes/order.$orderId.tsx` loads the order through `getOrderFn` / `loadOrder` (`src/server/commerce/orders.ts`). A public code alone is insufficient: access requires the owning customer, authorized staff, or the matching receipt cookie/token hash. `OrderDetail` shows unpaid/hold messaging; its cancellation control is gated by staff `orders.write`, not a general guest payment action. The page does not offer a payment-start action. The order UI and payment notes explicitly say no external gateway is connected.
6. `releaseExpiredHolds` (`src/server/commerce/holds.ts`) is invoked opportunistically by cart resolution and order-list/order-detail reads, processes at most 40 due orders per call, and transactionally marks unpaid holds expired/releases reserved stock and restores coupon usage where applicable. No scheduler was found in the inspected call sites. A 24-hour deadline is therefore not itself an immediate scheduled sweep.

Key files: `src/routes/cart.tsx`, `src/components/site/cart-view.tsx`, `src/routes/checkout.tsx`, `src/components/site/checkout-view.tsx`, `src/server/commerce/api.ts`, `src/server/commerce/cart.ts`, `src/server/commerce/checkout.ts`, `src/server/commerce/pricing.ts`, `src/server/commerce/holds.ts`, `src/server/commerce/release-hold.ts`, `src/routes/order.$orderId.tsx`, `src/server/commerce/orders.ts`, `src/components/site/order-view.tsx`, `src/server/auth/cookies.ts`, `src/lib/commerce-types.ts`.

## 2. Actual payment interface and persistence

`src/server/payments/service.ts` defines `PaymentProvider`:

- `key: "mock" | "zarinpal" | "zibal" | "idpay"`;
- `configured(env?)`;
- `createIntent({ orderId, amountIrr, idempotencyKey }) → { authority: string | null }`;
- `verify({ authority, amountIrr, token }) → { ok: true, referenceId } | { ok: false, reason }`.

`resolvePaymentProvider` recognizes only those names; **PayPing is absent**. The three named gateways check their respective environment placeholder, but their intent and verification methods throw `GatewayNotConnected` even if configured. Mock requires `PAYMENT_PROVIDER=mock` and `ALLOW_MOCK_PAYMENT=1` in a non-production environment; production rejects it. There is no production caller of `captureVerifiedPayment` in the inspected source, and no payment callback route or start action.

`captureVerifiedPayment` is an internal helper, not an end-to-end gateway flow: it checks configuration, IRR and optional expected amount against the server order, checks replay/order state, **calls `createIntent` and then `verify` in the same invocation**, and only then uses a transaction to lock/recheck the order, capture held stock or revalidate/reacquire released stock for an expired order, mark paid/verified/captured, and insert payment, payment log, order event, internal notice and audit. A verified same-key replay for the same order/amount/currency returns `already`; failed/expired keys are terminal. A verification rejection records a failed payment; thrown errors or post-verification transaction failures need special reconciliation. Its success event text currently says no external gateway was called. It is not suitable as-is for a provider-issued authority created **before** a browser redirect.

Existing Drizzle models (`src/server/db/schema.ts`; migrations `0002_shahoo_foundation.sql`, `0003_commerce_cart.sql`, `0006_completion.sql`, `0008_batch_02.sql`):

- `orders`: unique `publicCode`, optional customer and address, server-calculated `subtotalIrr`, `discountIrr`, `shippingIrr`, `totalIrr`, coupon ID/code, unique nullable checkout `idempotencyKey`, `buyerKey`, receipt `accessTokenHash`, `stockHoldUntil`, `status`, `paymentStatus`, `stockState` and timestamps. `orderItems` are price/quantity snapshots; `orderEvents` track status history.
- `payments`: `id`, `orderId` FK, provider, status, `amountIrr`, nullable `authority` and `referenceId`, unique non-null payment `idempotencyKey`, `currency` default IRR, nullable `refundOfPaymentId`, timestamps; `payments_order_idx` indexes order ID. Migration `0008` enforces IRR and adds the refund self-FK. No authority uniqueness constraint is defined in these inspected models/migrations. `payment_logs` references a payment and contains event, JSON payload and timestamp.
- Refund handling in `src/server/commerce/fulfillment.ts` records ledger entries linked to verified source payments; `gateway: false` metadata makes clear it is not a gateway refund. Do not treat a ledger record as evidence of actual bank reimbursement.

The lifecycle helper `src/lib/commerce-integrity.ts` describes `pending`, `verified`, `failed`, `expired`; however, the current capture helper inserts terminal rows rather than creating a durable initiation record. Its verified path also inserts rather than updating an already-existing pending row with that same unique key. Schema capacity alone is not an implemented payment lifecycle.

## 3. Proposed Batch 09 connection points — not implemented

**Start:** After the unpaid order transaction succeeds, or from the existing authorized order detail as a retry/resume action, add a server-side payment-start operation. The client may request payment for a public code but the server must independently authorize the owning customer or receipt holder, load the order, check payable state/hold, derive amount and currency from its persisted total, and handle zero-total orders by an explicitly approved policy. Do not start payment inside the cart transaction or accept the browser's amount as authoritative. Preserve a usable unpaid order if initiation fails; prevent duplicate concurrent starts and bind each attempt to its own idempotency key.

**Redirect:** A server-created intent should be durably correlated to the correct order and attempt before directing the browser to an allowlisted provider destination. Store only necessary provider identifiers and safe diagnostic data. Do not infer a successful payment from creation of an intent or from navigation. Exact correlation design, provider return fields and allowed URL construction must be validated with PayPing documentation/panel in Batch 09; no schema change is prescribed here.

**Callback location (proposal only):** `src/routes/api.payment.payping.callback.ts` corresponding to `/api/payment/payping/callback`, using a TanStack Start `createFileRoute` server handler analogous to existing `src/routes/api.media-upload.ts`. This file/route does **not** currently exist. Choose GET and/or POST only after checking PayPing's actual contract. Configure a fixed public HTTPS callback URL from trusted server configuration, not the request Host header; regenerate the route tree through normal tooling when a real route is added. Distinguish a browser return from any provider server notification if the provider supports both. Do not require customer cookies for server-to-server callback correlation; the existing receipt/session cookies are `SameSite=Lax` and may be absent on cross-site POSTs. Redirect the browser to an authorized order page or a safe neutral result without leaking the receipt token.

**Verification:** Treat callback parameters, status, public code and amount as untrusted hints. Locate the original server-side attempt/authority, authenticate/validate the callback as the provider contract permits, and perform server-to-server verification using the stored attempt and expected server order amount/currency. A return URL or reported success is not verification. Verify provider transaction identity, amount/unit, merchant and replay semantics as supported. Never log credentials, complete callback secrets or OTP values.

**Finalization:** Only after successful provider verification, transactionally serialize against other callbacks, cancellation and expiry; recheck order/attempt, record the verified result once, capture held stock or apply an explicitly reviewed late-payment/recovery policy, and record order/payment/audit events. Redirect/UI must read the persisted final state. A duplicate callback should be safe and deterministic; reject mismatched order/attempt/amount/currency and do not allow a failed key to silently become success. Handle pending/unknown results and retryable transport failures separately from a definitive provider rejection. Preserve evidence and an operator reconciliation/refund path if money was verified but stock, database commit, callback or cancellation prevents fulfillment. No fake success.

`APP_URL` is currently an SEO origin with a request-origin fallback (`src/server/seo/origin.ts`), not a callback setting. The fallback and `publicOrigin`'s acceptance of HTTP do not by themselves meet a trusted production callback policy. Existing CSP (`src/lib/security-headers.ts`) has `form-action 'self'` and `connect-src 'self'`; review the exact provider redirect/form mechanism rather than weakening CSP broadly.

## 4. Actual SMS interfaces and OTP flow

`src/server/sms/providers.ts` defines `SmsProvider` with key `kavenegar | smsir | mock` and `send(mobile, message): Promise<void>`. `resolveSmsProvider` allows mock only with both `SMS_PROVIDER=mock` and `ALLOW_MOCK_SMS=1` outside production. Real adapters resolve only when `NODE_ENV=production`, `SMS_LIVE=1`, and both `SMS_PROVIDER` and `SMS_API_KEY` are nonempty; `SMS_SENDER` is optional in code. `smsir` and `sms.ir` both select the SMS.ir adapter.

**Important existing code, not an integration claim:** Kavenegar's adapter performs an HTTP POST and checks HTTP plus its parsed return status. SMS.ir's adapter already has a `fetch` to a bulk-send endpoint using `x-api-key`, sender, message and mobile; it checks only HTTP status, not an application-level result or delivery. It is a generic bulk-message adapter, not a separate SMS.ir verification-template implementation. If explicitly configured with production live gates, this source can attempt network SMS. No claim is made about deployment configuration, provider acceptance or delivery. `.env.example` calls SMS disconnected, but the source-level live-gated adapter exists.

Actual OTP sequence:

1. `/account` uses `AccountPanel` (`src/components/site/account-panel.tsx`) and POST `requestCustomerOtpFn` / `verifyCustomerOtpFn` (`src/server/auth/api.ts`). `requestCustomerOtp` normalizes an Iranian mobile and reserves DB-backed, row-locked mobile/IP rate buckets (`src/server/auth/otp-limit.ts`). Limits: 60-second resend, five sends per mobile in 15 minutes, and if IP is available 20 per IP in 30 minutes. The rate slot is reserved before inactive-user and provider-availability checks.
2. The server generates a cryptographically random five-digit code, stores only its salted scrypt hash in `otp_challenges` with two-minute expiry and five-attempt limit, then `deliverLoginCode` uses the DB `otp` text template and calls generic `send`. OTP notices store a masked recipient and non-code body (`held`, `sent`, or `failed`); failure/unavailable consumes the challenge and returns an error. The `otp` template's `isActive` field is not checked in that lookup. `sent` means the adapter returned without throwing, not confirmed handset delivery.
3. The verify POST normalizes code/mobile, reads the latest unconsumed challenge, checks expiry, conditionally increments attempts, checks the hash, marks outstanding login challenges consumed, creates or uses the active customer, sets a hashed-token session/HttpOnly cookie, claims the guest cart and attaches eligible guest receipts. Only a non-production `ECHO_OTP=1` with neither both SMS provider and key configured returns `previewCode`. Mocks are prohibited in production. The mock SMS sender is a no-op; when the preceding `smsIsConfigured` check is also satisfied it can be reported as `sent`, not actual delivery.

OTP data models are `otpChallenges`, `otpRequestBuckets` (composite scope/subject hash primary key), `customerSessions`, `smsTemplates` and `notifications` in `src/server/db/schema.ts`. `src/server/db/seed.ts` seeds `otp`, `order_confirmed`, `payment_confirmed`, `shipped`, `cancelled` templates; this does not mean transactional SMS is dispatched.

**Separate future purposes:** OTP verification SMS should use the provider's verified/approved authentication-template or verification mechanism if required, passing the code only server-to-server and keeping challenge verification, expiration, throttles and no-plaintext logging under application control. Ordinary order/payment/shipment SMS should use independently approved transactional templates/lines and a post-commit delivery mechanism with explicit failure, retry, deduplication and privacy policy. `src/server/notify/events.ts` currently only inserts `channel=internal`, `status=stored` notices for order/support events; it never sends SMS. A stored internal notice, HTTP 2xx, or a seeded template is not confirmed delivery. Do not send an external message inside a database transaction before its commit.

## 6. Open integration risks and future verification

- **Lifecycle gap:** Current `captureVerifiedPayment` creates a fresh intent immediately before verification, has no connected callback or persisted start/redirect flow, and does not update an existing pending attempt. The interface needs careful redesign for PayPing without removing existing transactional safeguards.
- **Money vs. inventory/DB gap:** Provider verification occurs before the order transaction. If verification succeeds but stock recovery fails, cancellation races, or the transaction/connection fails, the code can return failure without inserting a verified payment. Do not lose the provider-side success; design explicit reconciliation and refund/manual handling. Recovery also does not re-consume a coupon restored on hold expiry; establish a policy.
- **Expiry gap:** Sweeping is lazy and capped at 40. The current payable test checks order state, not `stockHoldUntil` directly; an overdue but unswept `awaiting_payment` order can still appear payable to the internal helper. Decide deadline semantics and expiry/payment race behavior explicitly.
- **OTP concurrency/response gaps:** The correct-code path increments attempts then consumes challenges separately without claiming the specific challenge via a checked conditional success transition; concurrent valid submissions may both proceed to session creation. Verify and address this in the appropriate future work. SMS.ir checks HTTP status only; provider-level rejection/delivery ambiguity and unsupported verification-template requirements remain unresolved. SMS availability and retry behavior must be tested without leaking the code.
- **Security and UX gaps:** Public order codes are not authorization; an asynchronous callback must correlate independently of cookies while start/order views preserve ownership. Decide how guests resume/retry after a missing receipt cookie, how to avoid open redirects, and how to handle zero amounts, stale holds, invalid/cancelled/duplicate callbacks and verified-after-expiry or cancelled payments. Current payment event/note text explicitly says no external gateway; revise only when the actual behavior supports it.
- **Existing rules to preserve:** Server prices and IRR, row locks/conditional stock and coupon updates, checkout and payment idempotency, single stock capture, permission checks, and production mock/OTP-echo prohibitions. Refund ledger entries are not bank refunds.
